## Summary

Define a lightweight **Correction of Error (CoE)** process for governance/traceability incidents: a blameless, repeatable way to analyse *why* an error occurred, classify its severity, and produce actionable corrections (mitigations, tripwires, documentation fixes) without bundling those fixes into the CoE itself.

The name and structure follow Amazon’s Correction of Error practice — **correction** is the goal; cause analysis (including 5 Whys and structured incident questions) is the method.

This CIP is prompted by the “own goal” documented in **CIP-0015**: implementing governance behaviour before documenting the HOW/DO layer.

## Motivation

Human authorship and accountability implies not just “a name in metadata”, but a repeatable way to **correct course when we get it wrong**:
- identify the *cause(s)* of the error (not just the symptoms),
- classify severity and scope,
- and produce the right-sized remediation and prevention actions.

The key design constraint is **lightweightness**: minor internal governance mistakes should be easy to correct, while customer/deployed impact should trigger a stronger response. Blamelessness is required: focus on process, tooling, and design — not the operator.

## Detailed Description

### Naming: Correction of Error (not “Cause of Error”)

Earlier drafts used “Cause of Error.” That undersold the purpose. Amazon’s COE process is **Correction of Error(s)**: a post-incident mechanism whose primary outputs are corrective actions. Root-cause analysis (5 Whys, incident questions) serves correction; it is not the end product.

VibeSafe keeps the `coe/` acronym and directory, with the expanded name **Correction of Error**.

### What counts as a governance/traceability CoE incident

CoE analysis applies when we discover any of:
- a policy encoded in code without the expected planning artifacts (missing requirement/CIP/backlog),
- a traceability break (e.g. downward links where forbidden, missing links where required),
- an enforcement/validator change that wasn’t documented,
- template/runtime drift that could affect users on install/update,
- any customer/deployment-impacting workflow regression introduced by governance tooling.

### Scope: what kinds of changes are “governance sensitive”

Changes touching any of:
- `scripts/validate_vibesafe_structure.py` (and template copies)
- `scripts/whats_next.py` (and template copies)
- install scripts / deployment of system files
- templates that define user-facing process (CIP/backlog/requirements templates, cursor rules)
- rule changes that affect bottom-up linking / exception paths / enforcement semantics

### Severity classification (lightweight by default)

Classify each incident as one of:
- **Class 0 (Minor / internal-only)**: process slip with no user-facing impact (e.g. missing CIP for a validator rule change).
  - Typical outputs: short retrospective CIP/backlog note; optional tripwire warning.
  - Analysis depth: abbreviated OK — short 5 Whys (or fewer) and light incident questions.
- **Class 1 (Workflow-impacting)**: impacts contributors/maintainers (e.g. validation suddenly blocks common edits; install/update drift).
  - Typical outputs: retrospective CIP + backlog task; tests; possible notes.
  - Analysis depth: full 5 Whys + full incident questions required.
- **Class 2+ (External-impacting)**: anything that affects downstream users/projects, deployed behaviour, customer outcomes, or legal/regulatory exposure.
  - Typical outputs: retrospective CIP + explicit remediation plan (backlog tasks), validation hook(s), and a defined communication step.
  - Analysis depth: full 5 Whys + full incident questions + timeline; metrics where available.

**Note (mapping to “Sev” scales)**: We intentionally stop at “2+” for now. More severe sub-classes (e.g. security incidents, legal/regulatory violations) may exist, but we defer documenting a full taxonomy until we have real cases and a clear need.

Many orgs use **inverse-numbered Sev scales** where **Sev 1 is most severe** and higher numbers are less severe. Our **Class scale increases with severity** (Class 0 < Class 1 < Class 2+), but the boundary between Class 1 and Class 2+ can be fuzzy: workflow/documentation breakage can become external if it affects published docs, installs, or downstream users.

So treat any Sev mapping as *directional only*, and classify primarily by **blast radius**:
- **Class 0**: internal-only, easily reversible, low blast radius (often “lower Sev”, e.g. Sev 4–5).
- **Class 1**: maintainer/contributor workflow impact *that is not yet externally impactful* (often still “lower Sev”, e.g. Sev 4–3).
- **Class 2+**: any external impact (downstream users/projects, deployed behaviour, customer outcomes, legal/regulatory exposure) (often “worse Sev”, e.g. Sev 2–1).

**Why the Class scale starts at 0 (and is “unbounded”)**: Class is meant to be a **blast-radius index**. Class 0 is the baseline “internal-only” case. Class 1 is a larger radius (maintainers/contributors). Class 2+ is external. We write “2+” because we’re intentionally not defining the rest of the ladder yet—there may be larger radii in future (e.g. broad downstream breakage, safety/legal exposure, ecosystem-wide impact). This makes the Class scale naturally **unbounded**.

**Why the Class numbering direction is “reversed” vs Sev scales**: many Sev systems use **Sev 1 = worst** (numbers go *down* as severity goes *up*) because they’re optimized for paging/operations conventions. Our Class numbering goes *up* with blast radius because it’s an **analysis/traceability taxonomy** rather than an on-call paging taxonomy.

**Rule of thumb**: when uncertain, **classify upward** (prefer a false positive escalation over missing external impact).

### Where CoEs sit in the VibeSafe hierarchy

CoEs are **orthogonal** to the WHY→WHAT→HOW→DO hierarchy — they don't live within it, they *examine* it and *produce* items for it.

The standard hierarchy is:
```
Tenets (WHY) → Requirements (WHAT) → CIPs (HOW) → Backlog (DO)
```

A CoE has two parts that each have a different relationship to this hierarchy:

1. **"What went wrong"** — a diagnostic. This is *not* a requirement, because the mistake might *be* a missing requirement (or missing tenet, CIP, or backlog task). It's a cross-cutting retrospective that identifies *where* the hierarchy broke down.

2. **"How do we correct it"** — outputs at the appropriate level. Depending on severity and what broke, a CoE spawns items *into* the hierarchy:
   - Missing tenet? → add/update a tenet (WHY)
   - Missing requirement? → add a requirement (WHAT)
   - Missing CIP? → add a CIP (HOW)
   - Missing backlog task? → add a backlog task (DO)
   - Validation/tooling gap? → add a tripwire or validator rule

This is why a CoE can lead to requirements, CIPs, backlog items, or tenet updates — sometimes all of them from a single incident. The CoE itself is the "meta-level" artifact that bridges the gap analysis to the remediation, without being any one of those things itself.

### CoE document structure (Amazon-aligned, VibeSafe-adapted)

Amazon’s COE anatomy (Summary, Impact, Timeline, Metrics, Incident questions, 5 Whys, Action items, Related items) maps as follows:

| Amazon section | VibeSafe CoE section | Notes |
|---|---|---|
| Summary | Summary | Written last; stand-alone stakeholder-readable |
| Impact | Impact + Severity | Includes Class 0/1/2+ blast-radius classification |
| Timeline | Timeline | Required for Class 1+; optional for Class 0 |
| Metrics | Evidence / metrics | Optional; validator output, git history, install logs |
| Incident questions | Incident questions (10) | Detect / Diagnose / Mitigate — adapted for governance |
| 5 Whys | 5 Whys | Continue past five if needed; never stop at “human error” |
| Action items | Follow-up outputs | Spawned CIPs / backlog / requirements / tripwires |
| Related items | Related + `spawned_*` frontmatter | Links back into the hierarchy |

### Incident questions (the “10”)

Adapted from Amazon’s Detect / Diagnose / Mitigate set. “Customer impact” becomes impact on contributors, downstream projects, installs, or external users — depending on Class.

**Detection (3)**
1. When did you learn there was impact?
2. How did you learn there was impact? (validator, `whats-next`, human review, user report, …)
3. How can we reduce the time-to-detect in half?

**Diagnosis (3)**
4. What was the underlying cause of the impact?
5. Was an internal activity underway during the incident? (install/update, CIP implementation, rule change, refactor, …)
6. How can we reduce the time-to-diagnose in half?

**Mitigation (4)**
7. When did impact return to pre-incident levels (or when will it)?
8. How does the owner know the system/process is properly restored?
9. How did you determine where and how to mitigate?
10. How can we reduce the time-to-mitigate in half?

### 5 Whys

Ask “why” at least five times, or more until the chain reaches a correctable root (process, tooling, design, missing artifact) — not “human error.”

After each Why, check:
- Is this the underlying root cause?
- Could this have been detected before it happened?
- If the answer is human error: why was that error possible? (continue)

Each answer that identifies a gap should feed a follow-up output (prevention, detection, or faster mitigation).

### CoE workflow (post-incident)

- **Single-threaded owner**: one named human owns the correction and follow-through.
- **CoE write-up**: Summary, Impact, Timeline (as needed), Evidence, Incident questions, 5 Whys, Follow-up outputs.
- **Outputs, not implementation**: CoE produces backlog tasks / CIPs / changes to validation tripwires; those are implemented separately.
- **Blameless**: critique systems and process, not people.

### Agent-prompt / LLM compatibility (required for first-class components)

CoE is a first-class VibeSafe process. Like CIPs, backlog, requirements, and tenets, it must be present in **all** AI assistant context surfaces — not only in `whats-next` output.

| Surface | Artifact | Role |
|---------|----------|------|
| Canonical source | `templates/prompts/context-specific/coe.md` | Single source of truth for prompt text |
| Cursor | `.cursor/rules/coe.mdc` | Always-applied / path-globbed rule |
| Claude Code | `CLAUDE.md` | Generated project memory |
| Codex | `AGENTS.md` | Generated agent documentation |
| GitHub Copilot | `.github/copilot-instructions.md` | Generated instructions |

Install generates the platform files from `templates/prompts/` via `generate_prompts_for_platform` in `scripts/install-minimal.sh`. Legacy fallback also copies `templates/.cursor/rules/coe.mdc`.

**Acceptance criterion**: an LLM starting a session with only the installed agent prompts (without having read CIP-0016) can explain what a CoE is, when to write one, the status flow, and how it relates to WHY→WHAT→HOW→DO.

Shipping `coe/` + `whats-next` scanning without this prompt layer is a process gap (dogfooded in `coe/2026-10-04_missing-agent-prompt-integration.md`).

### Preventative tripwires (optional, not heavy gates)

We still want early detection, but not heavyweight “before it lands” process:
- git-aware warnings for governance drift (implementation changed without CIP/backlog updates),
- traceability gap warnings (tenets/requirements + implementation changed without CIP/backlog updates),
- template/runtime drift enforcement (already present).

### Validation hooks (preventing repeats)

Add (or extend) automated checks to detect:
- **Implementation changed** without any **CIP/backlog** change (governance drift)
- **Tenet/requirement changed** with implementation change but no CIP/backlog update (traceability gap)
- Templates drift from runtime files (already enforced)

Design principle: these checks should be warnings by default and become strict in CI/`--strict` mode.

### Checklist

- [ ] What severity class is this CoE?
- [ ] Who is the single-threaded owner?
- [ ] What is the impact (internal/workflow/user/deployed)?
- [ ] Timeline documented (required Class 1+; optional Class 0)?
- [ ] Incident questions answered (Detect / Diagnose / Mitigate)?
- [ ] 5 Whys completed (abbreviated OK for Class 0; full for Class 1+)?
- [ ] What traceability artifact(s) were missing or incorrect (tenet/requirement/CIP/backlog)?
- [ ] What follow-ups are required (mitigation tasks, documentation, tripwires) — with owner?
- [ ] Follow-up outputs created and linked (`spawned_*`)?
- [ ] Status moved Open → Analysed → Closed as work completes?

## Backward Compatibility

Must avoid turning normal work into heavy ceremony:
- default to warnings (opt-in strictness),
- keep Class 0 write-ups short (abbreviated 5 Whys / light questions OK),
- require full Amazon-style depth only for Class 1+,
- and scope the process to governance-sensitive file sets.

Renaming “Cause” → “Correction” does not change the `coe/` directory, file naming, status flow, or frontmatter schema.

## Testing Strategy

- Unit tests for any new validator rule(s).
- Integration check: run validator on repo + ensure expected warnings appear for deliberate “bad” examples.
- Template review: a Class 0 CoE can be completed without ceremony; a Class 1+ CoE has filled Incident questions and 5 Whys.

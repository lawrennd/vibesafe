# CIP-0017: Local Function Hooks for whats-next

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved, ready to start work
- [x] In Progress - Actively being implemented
- [x] Implemented - Work complete, awaiting verification
- [ ] Closed - Verified and complete

## Summary

Allow projects to extend `whats-next` output by providing a local Python module
(`.vibesafe/whats_next_local.py`) that defines project-specific sections and
next-step recommendations. VibeSafe core remains unchanged; user-defined logic
is discovered and called at well-defined integration points.

## Motivation

`whats-next` is a core workflow tool, but its output is fixed to VibeSafe's own
components (CIPs, backlog, requirements, tenets, Git status). Many projects have
additional concerns — active notebooks, dataset freshness, experiment tracking,
deployment readiness, CI status — that are invisible to the VibeSafe script.

Without an extension mechanism, projects either:
1. Maintain a separate, bespoke status script alongside `whats-next`, creating
   duplication and context-switching, or
2. Accept that `whats-next` only tells part of the story.

A local hook system lets each project teach `whats-next` about its own domain,
producing a single, unified view of "what to do next" rather than two.

This also aligns with the VibeSafe tenet of **User Autonomy Over Prescription**:
VibeSafe provides the framework and integration points; the project defines the
content.

## Detailed Description

### Design Principles

1. **Zero cost when absent** — if no local module exists, `whats-next` behaves
   exactly as today. No warnings, no errors.
2. **Minimal interface** — the local module exposes at most two optional
   functions with a simple, stable signature.
3. **No new dependencies** — the local module runs in the same Python environment
   as `whats-next`; no extra packages are required by the framework itself.
4. **Safe isolation** — errors in local code are caught and reported as warnings;
   they never crash the main script.
5. **Conventional location** — the module lives at `.vibesafe/whats_next_local.py`,
   following the existing `.vibesafe/` configuration convention.

### Integration Points

`whats-next` will call into the local module at two points:

#### 1. `get_local_sections(context) -> list`

Called twice — once before and once after the built-in sections are printed.
Each call passes a `position` key in the context (`"before"` or `"after"`).
Returns a list of section descriptors; each descriptor is either:

- A 2-tuple `(title, lines)` — position defaults to `"after"`
- A 3-tuple `(title, lines, position)` — where `position` is `"before"` or
  `"after"`

`"before"` sections are printed before all VibeSafe built-in sections (useful
for project-wide alerts or blockers). `"after"` sections are printed at the end
(useful for supplementary information).

```python
def get_local_sections(context: dict) -> list:
    """Return additional output sections for whats-next.

    Args:
        context: Dict containing git_info, cips_info, backlog_info,
                 requirements_info, args, and 'position' ("before"|"after").

    Returns:
        List of section descriptors. Each item is either:
          (title, lines)              → printed at "after" position
          (title, lines, position)    → printed at the given position
    """
    ...
```

#### 2. `get_local_next_steps(context) -> list`

Called inside `generate_next_steps()`. Returns a list where each item is either:

- A plain `str` — priority defaults to `"low"` (appended after all VibeSafe
  suggestions)
- A 2-tuple `("high", str)` — prepended before all VibeSafe suggestions
- A 2-tuple `("low", str)` — appended after all VibeSafe suggestions (same as
  plain string)

`"high"` items are intended for urgent, project-specific concerns that should
be seen before any VibeSafe housekeeping (e.g. "pipeline failed", "deadline
today"). Plain strings and `"low"` items are for lower-priority notes.
Intentional interleaving within VibeSafe's own list is out of scope — that
would require understanding VibeSafe's internal ordering and would couple local
code too tightly to VibeSafe internals.

```python
def get_local_next_steps(context: dict) -> list:
    """Return additional next-step suggestions for whats-next.

    Args:
        context: Same dict as above (without 'position').

    Returns:
        List of suggestions. Each item is either:
          str                → appended after VibeSafe suggestions ("low")
          ("high", str)      → prepended before VibeSafe suggestions
          ("low",  str)      → appended after VibeSafe suggestions
    """
    ...
```

Both functions are optional; the module may define either, both, or neither.

### Discovery and Loading Mechanism

```
Project root/
├── .vibesafe/
│   └── whats_next_local.py   ← discovered here
└── scripts/
    └── whats_next.py         ← VibeSafe core (unchanged)
```

The loading sequence in `whats_next.py`:

```python
import importlib.util, sys, traceback

def _load_local_module(path=".vibesafe/whats_next_local.py"):
    if not os.path.exists(path):
        return None
    try:
        spec = importlib.util.spec_from_file_location("whats_next_local", path)
        mod = importlib.util.module_from_spec(spec)
        spec.loader.exec_module(mod)
        return mod
    except Exception as exc:
        print(f"⚠️  Warning: could not load {path}: {exc}")
        return None
```

Calls to `get_local_sections` and `get_local_next_steps` are wrapped in
`try/except` so a buggy local module degrades gracefully.

### Context Dictionary

The `context` dict passed to both hooks contains:

| Key | Type | Description |
|-----|------|-------------|
| `git_info` | `dict` | Output of `get_git_status()` |
| `cips_info` | `dict` | Output of `scan_cips()` |
| `backlog_info` | `dict` | Output of `scan_backlog()` |
| `requirements_info` | `dict` | Output of `scan_requirements()` |
| `args` | `argparse.Namespace` | CLI arguments (e.g. `args.quiet`) |

The dict is read-only from the local module's perspective; mutating it has no
effect on the core script.

### Example Local Module (for a data science project)

```python
# .vibesafe/whats_next_local.py
import os
from pathlib import Path
from datetime import datetime, timedelta

def get_local_sections(context):
    sections = []
    position = context.get("position", "after")

    if position == "before":
        # Show a blocker banner before VibeSafe sections if CI is failing
        ci_flag = Path(".ci-failing")
        if ci_flag.exists():
            sections.append(("⛔ CI Failing", ["  Fix CI before merging."], "before"))

    if position == "after":
        # Show dataset freshness after VibeSafe sections
        data_dir = Path("data/processed")
        if data_dir.exists():
            stale = [
                f for f in data_dir.glob("*.parquet")
                if (datetime.now() - datetime.fromtimestamp(f.stat().st_mtime))
                   > timedelta(days=7)
            ]
            lines = [f"  - {f.name}" for f in stale] or ["  All datasets are fresh."]
            sections.append(("Data Freshness", lines))  # defaults to "after"

    return sections

def get_local_next_steps(context):
    steps = []
    # High priority: pipeline must run before anything else
    if not Path("results/latest_run.json").exists():
        steps.append(("high", "Run the pipeline: make run"))
    # Low priority: tidy up after a successful run
    if Path("tmp/").exists():
        steps.append("Clean up tmp/: rm -rf tmp/")
    return steps
```

### Template Stub

A stub `.vibesafe/whats_next_local.py` will be added to the VibeSafe templates
(but **not** installed automatically — users opt in by creating the file).
The stub documents both hooks with docstrings and a commented example.

## Implementation Plan

1. **Add `_load_local_module()` helper** to `templates/scripts/whats_next.py`
   - Discovers `.vibesafe/whats_next_local.py`
   - Returns module or `None`
   - Catches and prints import errors as warnings

2. **Extend `generate_next_steps()`** to call `get_local_next_steps(context)`:
   - Parse each returned item: plain `str` → "low", tuple `(priority, str)` →
     use declared priority
   - Prepend `"high"` items before VibeSafe suggestions; append `"low"` items after

3. **Extend `main()`** to call `get_local_sections(context)` twice:
   - First call with `context["position"] = "before"` — render matching sections
     before all built-in sections
   - Second call with `context["position"] = "after"` — render matching sections
     after all built-in sections
   - Each section rendered with `print_section()`; 2-tuples default to `"after"`

4. **Build `context` dict** in `main()` from already-computed scan results

5. **Add template stub** at `templates/.vibesafe/whats_next_local.py.example`
   (or similar) with full docstrings and a commented-out example

6. **Update tests** in `tests/test_whats_next.py`:
   - Test with no local module (existing behaviour unchanged)
   - Test with a valid local module returning sections and steps
   - Test with a broken local module (graceful degradation)

7. **Update documentation** in `docs/whats_next_script.md`

## Backward Compatibility

Fully backward compatible. The feature is triggered only if the user creates
`.vibesafe/whats_next_local.py`. Existing installations see no change in
behaviour.

## Testing Strategy

- Unit tests using `tmp_path` fixtures to create transient local modules
- Test both hooks present, one hook present, neither hook present
- Test exception in local module does not propagate to main output
- Test `context` dict has expected keys when hooks are called
- Test `get_local_next_steps` with: plain strings, `("high", …)` tuples,
  `("low", …)` tuples, and mixed lists; verify correct ordering in output
- Test `get_local_sections` with: 2-tuples (default to `"after"`),
  3-tuples with `"before"`, 3-tuples with `"after"`; verify sections appear
  in correct position relative to built-in sections
- Integration test: run `whats-next` against a fixture project containing a
  local module and verify sections and steps appear in the expected positions
